API 與 Worker 不直接通訊

API 寫入與 enqueue，Worker dequeue 與執行；任一方重啟不影響另一方。九條 import-linter 契約讓這條邊界變成 build fail。

Architecture · 一次 Run

每種 run 都走同一條路

01

Studio 發出請求

帶輸入、可選的 run_id（idempotent retry）、context、model override 或 draft 快照。

02

API 檢查、記錄、enqueue

Request guard、version 解析、allowlist；插入 run 列，狀態 queued；DBOS workflow id 等於 run id。

03

Worker 啟動，逐 step 執行

第一個 step 讀設定並標 running；之後每次 model request 與 tool call 是一個 step，event 連同 usage 同一 transaction 寫入。

04

Studio 即時觀看

Event 經 Postgres NOTIFY 到 API，以 SSE 送出；斷線後以最後 seq 續接。

05

以終態結束

completed、failed 或 needs_attention；heartbeat 每 5 秒，20 秒無 heartbeat 顯示 recovering。

Durable · 總覽 · Architecture

Agent、conversation turn、tool test、workflow、KB ingest、memory observe、retention，八種 run 都是這條路，差別只在 DBOS workflow 名稱與 queue。

Architecture · Durable execution 契約

五條規則，讓 Worker crash 變得安全

Crash matrix 在 19 個具名 crash point 以 kill -9 殺掉真實 process，逐條驗證。

一

一個 run 一個 workflow

Workflow id 等於 run id；重啟時 replay 已記錢的 step，不重跑。

二

Event idempotent、無空洞

唯一 event_key；seq 在 row lock 下配號；replay 回既有列。

三

Side effect：reserve、call、complete

斷在 call 之後進 needs_attention 交人判斷，不呼叫第二次。

四

非決定性全部記錄

時鐘、version 解析、環境上限、approval 期限都在 step 裡讀一次。

五

Step 錯誤可 replay

Exception 可 pickle，replay 時型別與訊息不變。

已知約束：DBOS 只恢復同一個 app version 的待定 workflow；部署頻繁時，跨天的 approval 等待需要版本策略（固定版本、滾動退場或 fork 遷移），尚待決定。

Durable · 總覽 · Architecture

第三條標橙色，是正確性問題而非省錢。底部的 app version 約束是目前最該先決定的運維議題。

Architecture · 核心主張

Run 的壽命由 database 決定，
不由 process 決定。

一次 run 跨分鐘到數天；process 隨時 deploy、重排、crash。兩者解耦，其餘目標才成立。

整份 Architecture 的一句話。前面五條契約、後面的取捨，都是為了這一句。

Architecture · 設計取捨

架構簡單，解法不是最小

決定選了沒選理由與代價
Durable executionDBOS，在 Postgres 內Temporal、自建 state machine不多一套服務；代價是恢復綁 app version
Queue 與通知DBOS queue + Postgres NOTIFYRedis、Kafka一個 database；NOTIFY 不持久，event 先落列

開發方法 · 角色

一個人與三類 agent，由獨立的 Reviewer 把關

人

方向與拍板

  • 定 milestone 範圍、非目標與邊界；邊界變動時拍板
  • 審核 plan 的決策表
  • 跑 browser check
  • 一句話拍板 merge

Orchestrator

計畫與調度

  • 研究並撰寫 milestone plan
  • 拆任務、排 wave、指派
  • 持有共用檔案順序與 migration lock
  • 收 review 結果、提交 commit

Implementer · Tester

實作與測試

  • 依任務 spec 實作
  • Tester 寫 plan 列名的測試，跑到綠、不 skip
  • 只改自己 Owns 的路徑
  • 測試不呼叫真實 LLM

Reviewer

獨立 review

  • 全新 context，只拿 diff 與任務原文
  • Critical、Important、Minor 分級
  • 每條帶檔案行號與失敗情境
  • 檢查品牌與授權規則

三類 agent 的組合每個 milestone 都調過，最後收斂到全部用同一家模型。Reviewer 的獨立性來自乾淨的 context，不是不同的模型。

開發方法 · Harness

邊界由 plan 與工具事先定義，agent 在邊界內實作

什麼時候拆分邊界

五種理由之一，否則不拆

  • 信任不同：tenant 的 workflow 是資料，平台的是程式碼
  • 壽命不同：run 活得比 process 久，狀態在 database
  • 故障域不同：API 與 Worker 不直接通訊
  • 依賴重量不同：API 不帶 Agent framework；純 package 無 I/O
  • 資源只能有一個主人：schema 只有 Alembic 能改

後端反模式

Reviewer 逐條檢查

  • 在 process 記憶體裡等待（sleep、polling、等 approval）
  • 非 idempotent 的 side effect；自動 retry 掩蓋錯誤
  • Replay step 裡的隱藏非決定性：時鐘、latest version
  • API 直接呼叫 Worker；應用程式碼改 schema
  • 跨 tenant 查詢少了 tenant 條件；用 LLM 判斷 branch
  • 巨大的 utils；重複實作既有函式；一次大 PR

邊界由人界定，Orchestrator 寫進 plan（Owns 欄、分層規則）。邊界會在 agent 的 context 中流失，所以迭代中由人介入調整：任務撞到邊界時 Implementer 停下回報，人拍板後才改契約、改 plan。完整文件：開發方法
