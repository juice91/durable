Durable · 核心主張

執行進度存在資料庫，
服務重啟也不會中斷。

一件工作可能要跑好幾天，服務卻隨時會因為部署或當機而重啟。進度存在資料庫，服務重啟後就從中斷的地方繼續。

整份簡報的一句話，放在最前面。後面的規格、五項保證與取捨，都建立在這句之上。

Spec · 功能

功能總覽

核心是 Durable：Agent 與 Workflow 的每一步都存進資料庫，能持久執行，也能重複執行。

核心

Durable 執行

  • 進度存在資料庫，服務重啟後從斷點接續
  • 對外動作只做一次，不因重跑而重複
  • 每次執行都有完整記錄：trace、token 用量與費用

Durable Agent

Agent

  • 每次 model request 與 tool call 都是一個存檔的 step
  • 每個 Agent 有自己的 model、指示與 tool（內建與 MCP）
  • 可使用 RAG 知識庫與 Memory

Durable Workflow

Workflow

  • 把多個 Agent 與 Tool 串成流程，每個 step 可指派不同的 Agent
  • 發佈後可重複執行：手動、排程或 API 觸發
  • 需要人決定時停在 Approval，可等待數天

 

隔離與管理

  • 資料依 tenant 隔離
  • Agent 與 Workflow 的設定有版本，可比較與還原
  • 輸出入檢查：PII 遮蔽、內容封鎖

Spec · 驗收

驗收標準

自動檢查

1. 全部測試通過且沒有 skip：import-linter、pytest（含 crash matrix）、API 接真實 Postgres、Studio vitest。

2. Crash matrix 的每個情境：side effect 只發生一次、seq 連續、run 以 completed 結束、SSE 重連結果一致。

3. Hosted CI 與自建 CI 在 main 上全部通過；每晚另外跑 worker 與 recovery 測試。

人工檢查

4. 建立 Agent、publish、在 Playground 執行，再看 trace、log、metrics，整條路徑走得通。

5. 含 Approval 的 Workflow：執行到 approval 停下，重啟 Worker，按下同意後流程跑完；decision event 只有一筆。

6. Knowledge 與 Memory：上傳文件、完成匯入、回答附上出處、更新 working memory；刪除使用者後 memory 一併清除。

Merge 條件：final review 沒有未解決的 Critical 或 Important；Studio 在各種螢幕寬度、深淺色、純鍵盤操作下都可正常使用，無障礙評分 95 以上。完整文件：Spec

Architecture · 全貌

系統架構

Console

Studio

Next.js · 設計、publish、執行、查看結果

Control plane

API

FastAPI · 驗證身分、建立 run、排入 queue、SSE

Single source of truth

Postgres

Run、event、queue、等待狀態、vector、memory

Execution

Worker

DBOS + Pydantic AI · 每完成一個 step 就存檔

API 與 Worker 不直接溝通

API 把 run 寫進 database 並排入 queue，Worker 從 queue 取出執行；任一方重啟都不影響另一方。這條界線由 import-linter 在 build 時強制檢查。

核心元件採用成熟開源方案

Agent loop、durable execution、vector search、telemetry 都使用成熟的開源元件；自行開發的是 policy、介面與整合規則。沒有額外引入 Redis、Kafka 或專用 vector DB。

Architecture · 一次 Run

執行生命週期

01

Studio 送出請求

帶上輸入、context、指定模型或 draft；以同一個 run_id 重送，也只會產生一個 run。

02

API 檢查、建立 run、排入 queue

檢查輸入、版本與模型 allowlist；建立狀態為 queued 的 run，DBOS workflow id 與 run id 相同。

03

Worker 逐 step 執行

每次 model request 或 tool call 都是一個 step；event 與用量在同一個 transaction 寫入後，才進入下一步。

04

Studio 即時顯示進度

新的 event 透過 Postgres NOTIFY 通知 API，再以 SSE 推到畫面；斷線後從最後一個 seq 接續。

05

Run 結束

以 completed、failed 或 needs_attention 結束；Worker 每 5 秒送出 heartbeat，超過 20 秒沒有回報就顯示為 recovering。

Durable · 總覽 · Architecture

Agent、conversation、tool 測試、workflow、KB 匯入、memory 整理、retention 清除，八種 run 都走這條路，差別只在 DBOS workflow 與 queue。

Architecture · Durable execution

持久執行的五項保證

Crash matrix 在 19 個具名中斷點以 kill -9 終止真實 process，逐項驗證。

一

每個 run 都能接續

Workflow id 等於 run id；重啟後 replay 已完成的 step，不重新執行。

二

Event 不漏、不重複

每筆 event 有唯一的 event_key；seq 依序編號；重複寫入只保留一筆。

三

Side effect 只發生一次

先預留、再呼叫、再記錄；若在呼叫後中斷，就進入 needs_attention，不呼叫第二次。

四

Replay 結果一致

時間、版本、期限這類會變動的值，只在 step 內讀取一次並保存。

五

錯誤也能 replay

Exception 完整保存，replay 時型別與訊息都不變。

已知限制：DBOS 只恢復同一個 app version 的 workflow；部署頻繁時，跨天等待的 approval 需要版本切換策略（固定版本、逐步淘汰舊版或分支遷移），目前尚未決定。

Durable · 總覽 · Architecture

第三項標橙色，因為它是正確性問題，不是效率問題。底部的 app version 限制是目前最需要先決定的運維議題。

開發方法 · 摘要

開發方法摘要

一人加 AI agent 在七天內實現這套系統：人決定範圍與邊界，agent 在邊界內實作，規則由工具自動檢查。

角色

人與三類 agent

  • 人決定範圍、邊界與是否 merge
  • Orchestrator 撰寫 plan、拆解並分派任務
  • Implementer 實作；Reviewer 以全新 context 獨立 review

流程

七個步驟

  • 撰寫 plan，人審核決策表
  • 依 wave 實作、測試、review、commit
  • 兩次整體 review 與 browser check 後，由人決定 merge

品質

四層關卡

  • 分層規則與測試由工具檢查，違反就無法 build
  • Crash matrix 以 kill -9 驗證持久執行
  • Critical 與 Important 全部解決才能 merge

開發方法 · 角色

角色分工

人

決定方向

  • 決定 milestone 的範圍、不做什麼與邊界；邊界需要調整時由人決定
  • 審核 plan 的決策表
  • 執行 browser check
  • 決定是否 merge

Orchestrator

規劃與分派

  • 研究並撰寫 milestone plan
  • 拆解任務、安排 wave、分派
  • 管理共用檔案的修改順序與 migration lock
  • 彙整 review 結果並提交 commit

Implementer · Tester

實作與測試

  • 依任務 spec 實作
  • Tester 撰寫 plan 指定的測試，全部通過、不 skip
  • 只修改分配到的檔案
  • 測試不呼叫真實 LLM

Reviewer

獨立 review

  • 使用全新 context，只看 diff 與任務原文
  • 問題分為 Critical、Important、Minor
  • 每個問題附上檔案位置與失敗情境
  • 檢查品牌與授權規則

三類 agent 的組合在每個 milestone 都調整過，最後全部採用同一家模型。Reviewer 的獨立性來自不共用 context，而不是換用不同的模型。

開發方法節開場。最核心的一條：Reviewer 只看 diff 與任務原文，不共用 Implementer 的 context；人不需要逐行閱讀程式碼。

開發方法 · 流程

開發流程

1

撰寫 milestone plan

由 Orchestrator 撰寫，包含任務表與決策表

2

人審核決策表

有不同意見時才介入

3

依 wave 執行

實作 → 測試 → review → commit；同一 wave 的任務修改不同檔案

4

Checkpoint review

第三個 wave 後整體檢查，修正後再繼續

5

Final review

由全新的 agent 檢查全部 diff

6

Browser check

人依 plan 中的操作清單，用真實資料走一遍

7

Merge main

沒有未解決的 Critical 或 Important，由人決定

多個 milestone 可同時進行，各自使用獨立的 branch 與 worktree；一個任務一個 commit，訊息附上任務編號。每個 milestone 的 review 與 browser check 都找出過問題，沒有一次是第一版就通過。

品質關卡

層級Gate內容
1 結構import-linter九條依賴規則：底層 package 不依賴上層；API 不 import Worker 或 Agent framework；只有 observability package 可以 import OpenTelemetry
2 單元測試pytest、vitest、tsc、lint測試使用 scripted model，不呼叫真實 LLM；Studio 的測試數量只能增加，commit 訊息需註明前後數量

4 Review 與人工任務 review → checkpoint → final → browser check問題分為 Critical、Important、Minor；前兩級全部解決才能 merge；browser check 涵蓋多種螢幕寬度、深淺色、純鍵盤操作與無障礙

開發方法 · Harness

邊界管理與常見反模式

什麼時候該拆分

符合以下任一項才拆

  • 信任程度不同：系統功能由平台開發並測試，在平台內執行；使用者自己的程式（例如外部 agent、MCP server）在平台外執行，Workflow 只透過呼叫來使用
  • 存活時間不同：run 比 process 活得久，狀態放在 database
  • 故障範圍不同：API 與 Worker 不直接溝通
  • 依賴輕重不同：API 不載入 Agent framework；純 package 不做 I/O
  • 資源只能有一個管理者：schema 只由 Alembic 修改

後端反模式

Reviewer 逐項檢查

  • 在 process 記憶體中等待（sleep、polling、等 approval）
  • Side effect 不具 idempotency；用自動 retry 掩蓋錯誤
  • Replay 時結果不一致：例如在 step 外讀取時間或最新版本
  • API 直接呼叫 Worker；應用程式碼直接修改 schema
  • 查詢漏掉 tenant 條件；讓 LLM 決定流程分支
  • 過大的 utils 檔；重複實作既有函式；一次提交過大的 PR

邊界由人決定，Orchestrator 寫進 plan（Owns 欄位、分層規則）。邊界會在 agent 的 context 中逐漸流失，因此過程中需要人介入調整：任務碰到邊界時，Implementer 停下回報，人確認後才調整規則與 plan。完整文件：開發方法

Durable · 總覽 · 開發方法

Harness 是包在模型外、讓它能實際執行工作的框架；它的任務之一是把邊界說清楚，讓 agent 不必猜。左邊給 Orchestrator 撰寫 plan 時使用，右邊給 Reviewer 使用；前八項反模式在 Durable 一律視為 Critical。
